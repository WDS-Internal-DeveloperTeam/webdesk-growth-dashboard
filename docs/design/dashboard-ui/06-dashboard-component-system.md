# Dashboard Component System

**Status:** Proposed, pending approval. Evaluates the full component inventory from the design
prompt (§27) against what `packages/ui` already has (5 components + 9 state components — see
`16-existing-shell-gap-analysis.md`) and what this system's real module specs actually need.
**Do not build a component "simply for the sake of having a large component library"** (design
prompt §27's own instruction) — every entry below is justified against a real, named use case from
the canonical specs, not built speculatively.

## 2. Core controls — new, required immediately (every module needs these)

| Component            | Spec                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Button**           | Variants: `primary` (accent fill), `secondary` (outline), `ghost` (text-only), `danger` (destructive, uses `colorTokens.danger`). Sizes: `sm`/`md`/`lg` per `05-dashboard-design-tokens.md` §7. Loading state built in (disables + shows a small inline spinner, never a separate wrapper).                                                                                                                                                              |
| **Icon button**      | Same variant/size system as Button, icon-only, always requires an `aria-label` prop (no visually-hidden-text escape hatch — enforced at the type level if practical). Used for row actions, the nav collapse toggle, the mobile hamburger.                                                                                                                                                                                                               |
| **Link**             | Wraps the existing injectable `linkComponent` pattern `packages/ui` already uses (so it stays framework-agnostic); visited/hover/focus states from the token set.                                                                                                                                                                                                                                                                                        |
| **Input**            | Text/URL/number share one component with a `type` prop. Label, description, error, required, disabled, read-only states all built in per `09-forms-and-validation.md`'s contract — not left to each form to hand-roll (a real, confirmed problem today: `apps/dashboard-web`'s existing pages mix inline styles, token imports, and raw CSS-variable strings inconsistently even within Phase 1F's own pages — see `16-existing-shell-gap-analysis.md`). |
| **Textarea**         | Same contract as Input, auto-growing up to a max height, then internally scrollable.                                                                                                                                                                                                                                                                                                                                                                     |
| **Select**           | Native `<select>` styled to the token system by default (matches the existing Project Switcher's own approach — see `16-existing-shell-gap-analysis.md`); a custom-rendered listbox is not built unless a real need for it (search-within-options, multi-line options) is identified for a specific module later.                                                                                                                                        |
| **Multi-select**     | A genuinely new pattern — tag/chip input backed by a listbox, needed for fields like Ready for Claude's dependencies or a page's target-keyword set. Built once, shared.                                                                                                                                                                                                                                                                                 |
| **Checkbox / Radio** | Standard, token-styled, always paired with a visible label (never icon-only).                                                                                                                                                                                                                                                                                                                                                                            |
| **Toggle**           | For boolean settings-style fields (e.g. System Settings module) — visually distinct from Checkbox (a toggle implies an immediate-effect setting; a checkbox implies a field value saved on form submit — this distinction is a deliberate UX signal, not interchangeable).                                                                                                                                                                               |
| **Date field**       | Native `<input type="date">`-backed by default (matches the Input philosophy — no custom calendar widget unless a real need, e.g. a date-range filter, is identified).                                                                                                                                                                                                                                                                                   |
| **Badge**            | The generic (non-status) badge — used for counts, tags, "New" markers. Distinct component from `StatusBadge`, which always carries a semantic-status color; a generic `Badge` defaults to neutral and accepts an explicit color override only for non-status labeling (e.g. a module's P0/P1/P2 priority tag).                                                                                                                                           |
| **Avatar**           | Initials-based by default (no photo-upload system exists); used in the new header user menu (`04-navigation-system.md`) and anywhere a record's owner/actor needs a compact visual identity.                                                                                                                                                                                                                                                             |

## 3. Structural / layout — new, required immediately

| Component      | Spec                                                                                                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Card**       | A bordered (Direction A) content container — see `05-dashboard-design-tokens.md` §5 for shadow/border rules. Used for the Home dashboard's widget tiles and for grouped form sections.                                                                              |
| **Table**      | The single canonical table system — see `08-tables-and-filters.md` for its full spec (sort, filter integration, pagination, row/bulk selection, responsive behavior, states). This is the highest-leverage single component in the whole system, per Principle 2.3. |
| **Tabs**       | Needed for Page Workspace's 16-tab pattern and any record editor with logically distinct sections too large for simple in-page scroll. Horizontal, overflow-scrollable on narrow viewports (never wraps to two rows).                                               |
| **Accordion**  | For secondary/advanced metadata that should default to collapsed — e.g. a record's raw audit-adjacent technical fields on a detail page.                                                                                                                            |
| **Pagination** | Offset-based, matching the existing live pattern (Previous/Next + implicit "there's more" detection via a limit+1 fetch, exactly as the Projects list page already does) — kept as the standard, not reinvented per module.                                         |

## 4. Navigation / overlay — new, required immediately

| Component               | Spec                                                                                                                                                                                                                                                                                          |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Drawer**              | Slides from the right, used for quick record preview, notifications (`04-navigation-system.md`), and any "don't lose your place in a list" interaction — see `17-side-panels-and-drawers` in `07-page-patterns.md` for exactly when to use a drawer vs. a full detail page.                   |
| **Modal**               | Confirmations and short, focused forms only — never multi-step workflows (design prompt §18's own rule). Must trap focus and restore it to the triggering element on close (a real, currently-unbuilt accessibility requirement — see `14-accessibility-requirements.md`).                    |
| **Tooltip**             | Short, non-interactive supplementary text only (e.g. an icon button's action name on hover) — never used to convey information not available elsewhere, since tooltips are unreliable on touch/keyboard-only access.                                                                          |
| **Dropdown**            | The generic overlay menu primitive underlying the header user menu, table row-action menus, and any "more actions" affordance.                                                                                                                                                                |
| **Command/action menu** | Justified by a real, specific need: the new global search (`04-navigation-system.md`) is exactly a command-palette pattern — `⌘K`, fuzzy-matches modules and records, keyboard-navigable. Not built as a generic pattern for its own sake; built because global search specifically needs it. |

## 5. Feedback — new, required immediately

| Component    | Spec                                                                                                                                                                                                                                                                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Alert**    | Full-width or inline banner for a page-level condition that needs attention but isn't a routine status (e.g. "Production release blocked — unresolved critical finding," per `01-visual-directions.md`'s Direction A status treatment). ## 7. Explicitly not built in this pass

No component is dropped from the design prompt's inventory outright, but two are deliberately
deferred rather than speculatively built now:

- **A second, code-diff-specific rendering mode for the Diff viewer** — until a real module
  requirement surfaces one (source-code review happens via GitHub PR links today, not in-app).
- **A rich/Markdown WYSIWYG editor** for the "Rich/Markdown content where approved" form-field type
  (design prompt §9) — until a specific module's task package identifies which fields need it and
  what subset of Markdown is actually approved for use; building a full editor speculatively risks
  over-scoping a form primitive that most modules won't need. A plain `Textarea` with monospace
  Markdown-source editing is the interim contract.

## 8. Governance note

Every component above uses only the token set in `05-dashboard-design-tokens.md` — no component
introduces a new color, spacing value, or typeface outside that token set. This is the mechanism
that keeps Principle 2.3 (Consistency) real rather than aspirational as 43 modules get built by
different task packages over time.
