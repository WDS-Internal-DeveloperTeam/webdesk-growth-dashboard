02Design decisions confirmed with the project owner

D1 — Version model Real multi-row version history

Mirrors Design Token Library / Section and Pattern Library — every version is its own physical row, sharing a stable recordId; exactly one row per record has isCurrent: true. Editing an approved record forks a new version rather than mutating in place, and a new version's own approval automatically supersedes whichever other version currently holds approved. Chosen over a simple mutable-row + integer version since wireframes are inherently revision-driven planning artifacts.

D2 — File field Plain URL reference, not a new attachment mechanism

fileReference is a nullable, safeHttpUrlSchema-validated URL (e.g. a Figma link), mirroring Brand Library's own field exactly. No new Blob upload infrastructure — none is provisioned in production.

D3 — relatedTemplateId Plain, unvalidated string — a real dependency cycle

The module-implementation roadmap flags page_template_library ↔ wireframe_library as a genuine, unresolved cycle in the seeded registry data: a template references its wireframe and a wireframe references the template it implements. Built before that cycle could be resolved — matching the established precedent (Website Strategy Center ↔ Internal Linking Library). Note: Page Template Library was merged to main concurrently with this build (see §04) — its own wireframeReferences field is likewise unvalidated for the identical reason, symmetric on both sides of the cycle.
