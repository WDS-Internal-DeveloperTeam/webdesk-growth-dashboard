01 What this branch builds

A single table with real multi-row version history (motion_interaction_records), mirroring Section and Pattern Library's structural pattern and Page Template Library's cross-module relationship pattern. Two design forks were confirmed directly with the project owner before any code was written, since the canonical spec (§18) gives no field list — only a bare taxonomy.

  • Field set — a 26-value category enum covering the spec's own taxonomy, plus 8 content fields (3 rich-text-sanitized, 3 plain code/spec values, designReference, relatedComponentIds), the standard 8-value approval workflow, and real version history.
  • Relationship validation — relatedComponentIds is a real, existence-validated relationship into Component Library (ComponentsService.existingComponentIds()), not an unvalidated array — a genuine improvement over the precedent set when Component Library didn't exist yet.

03 Independent code review

High effort — 8 parallel finder angles against git diff main...HEAD. 5 angles (line-by-line, cross-file tracer, reuse, efficiency, conventions) returned 0 candidates. 3 angles converged on the same candidate independently; deduped to two distinct findings plus one refuted duplicate.

Registry dependencies omitted a real coupling CONFIRMED FIXED
packages/database/src/migrations/00035-populate-module-registry-fields.ts

The seeded module_registry.dependencies for this module was null, but the branch's own build calls ComponentsService.existingComponentIds() on every create/update — a real, hard runtime dependency on Component Library, the same class of coupling page_template_library's own row already records. The roadmap doc computes build-order "waves" by transcribing this exact field, so a future maintainer sequencing work off it could deprioritize Component Library without seeing the real coupling. Fixed with an additive migration (00035 already ran in production) and the roadmap doc moved this module from Wave 1 to Wave 2.

Update DTO schema hand-duplicated, not derived PLAUSIBLE ACCEPTED DEBT
apps/dashboard-api/src/motion-and-interaction-library/motion-and-interaction-library.dto.ts

updateMotionInteractionRecordSchema hand-retypes 8 fields from the create schema instead of deriving via .omit()/.partial(). Content Template Library and Brand Library already fixed this exact shape — but verification found 6 of 8 other sibling modules checked still hand-duplicate the same way, including modules built after that fix landed. A real but inconsistently-applied convention in this codebase, not a rule this module uniquely broke — left as tracked debt rather than fixed in isolation.

"Unused speculative" existence-check method REFUTED
apps/dashboard-api/src/motion-and-interaction-library/motion-interactions.service.ts

3 independent finder angles flagged existingRecordIds()/findByIds() as zero-caller dead code, citing Page Template Library's own removed findByIds() as precedent. On verification this doesn't hold: unlike that removed method (no doc-comment rationale, orphaned tests), this one mirrors an established, already-realized convention — Section and Pattern Library's identical method, consumed by Page Template Library once it needed it — ships with an explicit doc-comment rationale, and has real, intentional test coverage.
