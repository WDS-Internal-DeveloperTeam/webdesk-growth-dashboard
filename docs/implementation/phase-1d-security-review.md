## Scope

- Centralized `AuthorizationService` (§13) and its retirement of `PermissionService`.
- The 43→21 module registry (`ModuleRegistryRepository`, migrations `00014`/`00015`).
- Project-scoped role assignment (`user_roles.project_id`, migration `00016`).
- Confidential-field actions (`view_confidential`/`edit_confidential`) and the redaction utility.
- `SeparationOfDutiesService`'s new cross-request check (`authorization_actions`, migration `00017`).
- Self-role-assignment blocking in `RoleAssignmentService` (resolves the gap the prior pass flagged).
- Super Admin bootstrap CLI (`bootstrap-super-admin.ts`).
- `GET /me/capabilities`, `GET /authz/modules`, `GET /authz/module-registry`.

Out of scope (unchanged from the prior pass, still not implemented): the 21 real business modules,
Task 7's general audit-log subsystem, any real business entity with confidential fields.

## STRIDE analysis

| Threat                                                                                                                    | Scenario                                                                                                                                                               | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Residual risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spoofing** — forged `separation_of_duties_denied` event to hide a real self-assignment attempt                          | A caller crafts a request hoping to trigger the event without the actual denial, muddying the audit trail                                                              | The event is recorded server-side, inside `RoleAssignmentService`'s own `assertNotSelfTargeting` wrapper, only on a real thrown `ForbiddenException` from `SeparationOfDutiesService` — there is no client-controlled path to emit this event type without the underlying denial actually occurring                                                                                                                                                                                           | None identified — the event and the denial are the same code path, not two independently triggerable actions                                                                                                                                                                                                                                                                                                                                                                           |
| **Tampering** — bypassing project-scoping via a crafted `projectId`                                                       | A caller who holds a role only in Project A supplies Project B's id, hoping `findRoleIdsForUser`'s `IN (NULL, projectId)` filter is misapplied                         | The filter is a single parameterized Sequelize `Op.in` query — no string concatenation, no client-supplied SQL fragment; verified against a real database in `phase1d-authz.integration.test.ts`'s "project-scoped authorization" suite, including the explicit case of a role held in Project A but checked against Project B                                                                                                                                                                | None identified for the current implementation. No HTTP route yet passes a `:projectId` param through to `PermissionGuard` (`permission.guard.ts`'s own doc comment notes this is forward-compatible, unexercised plumbing) — so this surface is not reachable over HTTP in this phase at all; the residual risk is entirely deferred to whichever future phase adds the first project-scoped route                                                                                    |
| **Tampering** — module-registry-to-permission-group remapping drift                                                       | The `permission_group_id` FK on a `module_registry` row is manually edited (e.g. a bad future migration) to point at a more permissive group than intended             | `module_registry.permission_group_id` is a real FK constraint (`RESTRICT`/`CASCADE`, migration `00014`) against `modules.id` — it cannot point at a non-existent group, and migration `00015`'s own `REGISTRY` mapping is the single source of truth, code-reviewed as part of this change                                                                                                                                                                                                    | The mapping itself (which of the 43 modules maps to which of the 21 permission groups) is this implementer's own reasoned cross-reference between two approved documents that don't cross-reference each other — explicitly flagged in migration `00015`'s own doc comment and `docs/implementation/phase-1d-permission-catalog.md §3` as needing the required second-role review, not asserted as definitely correct                                                                  |
| **Repudiation** — Super Admin bootstrap without a durable record                                                          | The very first Super Admin is created and there's no way to reconstruct who did it or when                                                                             | `bootstrap-super-admin.ts` records a `super_admin_bootstrap` auth event with `userId` and a `reason` string naming the email — verified by real CLI execution against a disposable database (created a test user, ran the compiled CLI, confirmed via `psql` that both the role assignment and the event row exist with the correct content)                                                                                                                                                  | Same free-text-`reason` limitation as every other Phase 1D event (see the prior pass's Repudiation row) — adequate for this phase, not a first-class structured audit record                                                                                                                                                                                                                                                                                                           |
| **Information Disclosure** — `/me/capabilities` leaking another user's grants                                             | A caller manipulates the request hoping to see a different user's effective capabilities                                                                               | `CapabilitiesController.getCapabilities` derives `userId` exclusively from `req.authUser!.id` (the session's own identity) — there is no `userId` request parameter of any kind for a caller to substitute; verified in `authz.e2e-spec.ts`'s "never exposes another user's capabilities" test, which confirms a low-privilege user's own capabilities never include a `users_roles` grant even when a Super Admin session queried in the same test run does                                  | None identified — there is no code path from any request input to a different user's id for this endpoint                                                                                                                                                                                                                                                                                                                                                                              |
| **Information Disclosure** — catalog endpoints (`/authz/modules`, `/authz/module-registry`) leaking the full grant matrix | A caller with only `users_roles:view` learns the complete 458-row grant matrix, not just module/registry names                                                         | Both endpoints return only `{id, key, name}` (`ModuleSummary`) or `{id, key, name, permissionGroupKey}` (`ModuleRegistrySummary`) — no `role_permissions` rows, no per-role grant data, are exposed by either route; verified in `catalog.service.spec.ts` and the real-database `authz.e2e-spec.ts` catalog tests                                                                                                                                                                            | Both routes are still gated by `users_roles:view` (same grant as the pre-existing `/authz/roles`), consistent with the existing "Users/roles" module boundary rather than being made public — this is a deliberate choice, not an oversight, since the module/registry names themselves reveal dashboard structure that only users with some administrative visibility should see                                                                                                      |
| **Elevation of Privilege** — self-assignment without dual control                                                         | A Super Admin actor calls `POST /authz/users/:actorOwnId/roles` on **themselves**                                                                                      | **Now blocked.** `RoleAssignmentService.assignRole`/`revokeRole` call `SeparationOfDutiesService.assertDistinctActors` before any repository access, throwing `ForbiddenException` and recording `separation_of_duties_denied` — verified end-to-end against a real database (`authz.e2e-spec.ts`'s "privilege escalation" suite, asserting both the HTTP 403 and the persisted event row) and at the unit level (`role-assignment.service.spec.ts`)                                          | This closes the prior pass's accepted-gap #1 entirely — there is no longer a path, even for Super Admin, to self-modify roles. One operational note carried over unchanged: this means a lone Super Admin who is demoted (by someone else) and needs re-promotion cannot self-serve; a second Super Admin (or the bootstrap CLI, which only works pre-first-admin) must act. This is the intended dual-control property, not a bug.                                                    |
| **Elevation of Privilege** — confidential-field grant escalation via role assignment                                      | A caller hopes that assigning any role also implicitly grants `view_confidential`/`edit_confidential`                                                                  | No role's seed data includes either action (`docs/implementation/phase-1d-permission-catalog.md §4`) — assigning a role only grants whatever `role_permissions` rows already exist for it, and zero confidential-field rows exist for any role; verified against real seeded data in `phase1d-authz.integration.test.ts`'s "no confidential-field grant is pre-seeded for any role" test (checked against Super Admin specifically, the role most likely to have an accidental blanket grant) | None identified for the current (unseeded) state. The residual risk is entirely in the _future_: whoever eventually grants a role's first `view_confidential`/`edit_confidential` row (via a not-yet-built grant-editing endpoint) must do so deliberately — that endpoint does not exist yet, so this cannot happen accidentally today                                                                                                                                                |
| **Elevation of Privilege** — Super Admin bootstrap race (two operators bootstrap concurrently)                            | Two operators run `bootstrap-super-admin` at nearly the same time, hoping to create two independent "first" Super Admins bypassing the intended single-bootstrap model | `anyUserHoldsRole` is checked before `assign()`, but this is a check-then-act pattern with the same narrow TOCTOU window the prior pass already accepted for `RoleAssignmentService.assignRole` (accepted-gap #4) — however, `user_roles`'s unique `(user_id, role_id)` constraint only prevents the _same_ user being double-assigned, not two _different_ users both becoming Super Admin via a true race                                                                                   | **Accepted residual risk, not fully closed.** This CLI is operator-run, non-HTTP, env-gated (`SUPER_ADMIN_BOOTSTRAP_ENABLED=true`), and used exactly once per real deployment by definition — the realistic threat model is a misconfigured deployment script, not an external attacker (no network path to this script exists). Not considered severe enough to warrant a distributed lock for a one-time bootstrap operation, but noted here rather than silently assumed race-free. |
| **Denial of Service** — `getEffectiveCapabilities` as an expensive-query vector                                           | A caller repeatedly hits `/me/capabilities` hoping to trigger an expensive per-module query fan-out                                                                    | Implemented as exactly two queries total regardless of role/module count (`findRoleIdsForUser` once, `listGrantsForRoles` once) — verified by a dedicated unit test asserting each is called exactly once (`authorization.service.spec.ts`'s "uses exactly one query for roles and one for grants" test)                                                                                                                                                                                      | Same general per-endpoint rate-limiting posture as every other authenticated route in this phase — no endpoint-specific additional throttling was added, consistent with the rest of the API surface                                                                                                                                                                                                                                                                                   |

## Summary of accepted/residual items (Phase 1D-expanded)

1. **Module-registry-to-permission-group mapping (migration `00015`) is this implementer's own
   cross-reference**, not drawn verbatim from a single approved source — flagged for the required
   second-role review (Tampering row above, and `docs/implementation/phase-1d-permission-catalog.md §3`).
2. **Super Admin bootstrap has a narrow concurrent-race window** between two operators — accepted
   given the CLI's operator-only, one-time-per-deployment, no-network-path threat model.
3. **Project-scoped authorization has no HTTP route yet** — the database/repository layer is fully
   built and tested, but `PermissionGuard`'s `:projectId` extraction is unexercised plumbing until
   a future phase adds the first project-scoped route.
4. **Confidential-field grant-editing has no dedicated endpoint** — the enforcement mechanism
   (`AuthorizationService.canViewConfidential`/`canEditConfidential`) is real and tested, but
   nothing can grant a confidential-field permission over HTTP yet; the only way to create one
   today would be a direct database write, which is out of this phase's own scope to build a UI for.
5. Every accepted gap from the prior pass (`docs/security/threat-model-authorization-rbac.md`)
   **except #1** (self-assignment, now closed above) carries forward unchanged: no persisted audit
   trail for denied permission checks beyond `auth_events`, no "list permissions for a role"
   endpoint, no dedicated concurrency test for the assign-role check-then-act race.

None of these are believed to constitute a critical, immediately-exploitable vulnerability at this
project's current stage (no production deployment, no real users, no external network path to the
bootstrap CLI) — they are scoped, documented risk-acceptance decisions consistent with
`docs/task-packages/phase-1d-rbac-permissions-expanded.md`'s explicit scope (§32), surfaced here
for the required second-role review rather than left implicit.

## Validation method

Every mitigation claimed above that references a specific test file was verified by actually
running that test: the full unit suite (144 tests, `pnpm --filter @webdesk/dashboard-api test`),
the real-database integration suite (`packages/database` — 41 tests) and e2e suite
(`dashboard-api` — 37 tests across `auth.e2e-spec.ts`/`authz.e2e-spec.ts`/`health.e2e-spec.ts`),
and the Super Admin bootstrap CLI's real end-to-end execution (creating a test user, running the
compiled script, confirming both the role assignment and the audit event via direct `psql`
queries, then testing all three refusal paths) — not asserted from reading the code alone. See
`docs/project-state/phase-1d-validation-report.md` for the full run record.
