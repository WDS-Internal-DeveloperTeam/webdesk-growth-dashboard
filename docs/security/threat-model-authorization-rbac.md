# Threat Model — Authorization / RBAC (Phase 1D)

**Status:** Draft STRIDE pass, produced per `docs/security/threat-model-plan.md`'s procedure at the
point the "Authorization" required-coverage area (ADR-0010) moved from Architecture Defined to
actual implementation. Covers exactly the scope
`docs/task-packages/phase-1d-rbac-authorization.md` implements — the 21 real business-module CRUD
endpoints, the confidential-field axis (`view_confidential`/`edit_confidential`), and the general
ADR-0017 audit-log subsystem (Task 7) are separate, not-yet-implemented areas with their own future
STRIDE passes or extensions of this one.

**Review status:** authored by the same agent that implemented this phase. Per
`docs/security/threat-model-plan.md`'s procedure and ADR-0010's separation-of-duties principle,
this pass requires review by a second, human role before the implementation is considered ready
for its QA gate (G4) — that second review has **not** happened yet. This document is a rigorous
self-review, not a substitute for it; do not treat it as satisfying the gate on its own.

---

## Scope

- Deny-by-default permission evaluation (`apps/dashboard-api/src/authz/permission.service.ts`).
- `PermissionGuard` + `@RequirePermission` composition with the pre-existing `SessionGuard`
  (`apps/dashboard-api/src/authz/permission.guard.ts`, `require-permission.decorator.ts`).
- The "Users/roles" module's own HTTP surface — the one real, self-consistent feature this phase
  builds to prove the framework (`apps/dashboard-api/src/authz/role-assignment.{service,controller}.ts`).
- Role-change session revocation (`RoleAssignmentService` calling `SessionService.revokeAllForUser`).
- The real, seeded role/module/permission matrix (`packages/database/src/migrations/00009`–`00013`).
- `SeparationOfDutiesService` as a reusable primitive (`apps/dashboard-api/src/auth/common/separation-of-duties.service.ts`)
  — already wired into `RecoveryService` (Phase 1C); this pass evaluates whether it is also needed,
  and currently is **not** applied, inside `RoleAssignmentService` itself (see Elevation of
  Privilege, "Users/roles" table, below).

## Out of scope for this pass

The 21 real business modules' own CRUD endpoints (`project_configuration`, `business_knowledge`,
etc.) — they don't exist as code yet; `PermissionGuard`/`@RequirePermission` is proven here only
against the "Users/roles" module's own endpoints, per the task package's explicit scope decision.
The confidential-field axis (`view_confidential`/`edit_confidential`) — deliberately not seeded
(migration `00013`'s own doc comment), so there is nothing to threat-model yet. Object-level
"(assigned)" scoping (Review Center, Change Center, Imports) — a future feature's own
responsibility. The general ADR-0017 audit-log subsystem (Task 7) — `auth_events` here remains the
same narrow, login/role-change-scoped log Phase 1C established, not the immutable, retained-7-years
subsystem. Vercel deployment/infrastructure-level concerns — assumed provided by the hosting
platform, not this application layer, same carve-out as the Phase 1C pass.

## STRIDE — Permission evaluation (`PermissionService` / `PermissionGuard`)

| Threat                                                            | Scenario                                                                                                                                                                                                    | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Residual risk                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spoofing** — acting as another user                             | An attacker tries to have a permission check evaluated against someone else's identity                                                                                                                      | `PermissionGuard` reads `request.authUser.id` exclusively from what `SessionGuard` already populated from a validated session — no request-supplied `userId` field is ever accepted as "who is asking"                                                                                                                                                                                                                                                                                                                                             | Depends entirely on `SessionGuard`'s own correctness, already covered by the Phase 1C threat-model pass; not re-litigated here                                                                                                                                                                                                                                                         |
| **Tampering** — role/module/permission rows altered at rest       | Database compromise inserts an unauthorized `role_permissions` grant, or reassigns a `user_roles` row                                                                                                       | No application-layer integrity check (e.g., signing) exists over these tables — same accepted-risk posture as password hashes / TOTP secrets in the Phase 1C pass: DB compromise is out of scope for an application-layer control, mitigated by infra-level DB access control, not this code                                                                                                                                                                                                                                                       | A compromised database can grant arbitrary privileges directly, bypassing every guard described here — an inherent limit of any DB-backed authorization model, not unique to this implementation                                                                                                                                                                                       |
| **Repudiation** — no record of _why_ a request was denied         | A user is denied access and there's no record to review afterward                                                                                                                                           | `PermissionGuard` throws a `ForbiddenException` with the specific `moduleKey:action` in its message, surfaced to the caller as the HTTP response and to server logs via `AllExceptionsFilter`                                                                                                                                                                                                                                                                                                                                                      | **Accepted gap**: denial events are not written to `auth_events` (or any persisted audit trail) — only the pre-existing `role_assigned`/`role_revoked` events are. A pattern of repeated denied attempts against a sensitive module is currently visible only in ephemeral request logs, not a queryable audit trail. Should be revisited once Task 7's general audit subsystem exists |
| **Information Disclosure** — permission-check side channel        | A caller probes multiple `moduleKey`/`action` pairs to map out what a target role can do, without ever holding sufficient permission to be told directly                                                    | Every denial path returns the identical `403 Missing permission: <moduleKey>:<action>` shape regardless of _why_ denial occurred (unknown module vs. no roles vs. no grant) — `PermissionService.can()` collapses all three to `false` before the guard ever sees a reason (`permission.service.ts`'s own doc comment: "there is no code path in this service that defaults to allow")                                                                                                                                                             | The error message itself echoes back the `moduleKey`/`action` the caller supplied (not a secret — it's the caller's own request), so this isn't user enumeration in the Phase 1C sense; an authenticated caller can still learn "I don't have X" for any X they choose to ask about, which is unavoidable for a permission check to be useful at all                                   |
| **Denial of Service** — @RequirePermission omitted on a new route | A future developer adds a route under an existing controller and forgets `@RequirePermission`                                                                                                               | `PermissionGuard.canActivate()` treats a missing decorator as a **developer error**, not "nothing to check," and fails closed with a 500 (verified in `permission.guard.spec.ts`'s first test) — an unprotected route is not silently reachable, it's loudly broken                                                                                                                                                                                                                                                                                | This is a deliberate fail-closed tradeoff: a misconfigured route becomes a visible 500 (caught in code review / integration tests / smoke tests) rather than a silent authorization bypass. The residual risk is availability (a broken route), never confidentiality/integrity (an over-permissive one) — the correct tradeoff for this system                                        |
| **Elevation of Privilege** — guard-ordering bypass                | An attacker hopes `PermissionGuard` runs before `SessionGuard`, seeing no `authUser` and mis-handling it as "allow"                                                                                         | `PermissionGuard` explicitly checks `if (!authUser) throw UnauthorizedException("Authentication required")` — it never defaults to allow on a missing identity, independent of guard _order_; verified directly in `permission.guard.spec.ts`'s second test. Guard order itself (`SessionGuard` class-level, then `PermissionGuard` method-level) is additionally verified indirectly by every e2e test in `authz.e2e-spec.ts`, since a session-less request against a `@RequirePermission`-guarded route consistently returns 401, not 403 or 200 | None identified — both the ordering _and_ the fail-safe check independently prevent this                                                                                                                                                                                                                                                                                               |
| **Elevation of Privilege** — confused deputy via module-key typo  | A route is annotated `@RequirePermission("users_roles", "veiw")` (misspelled action) or a non-existent module key, intending to require a real grant but actually requiring one that can never be satisfied | `PermissionService.can()` denies immediately on an unknown `moduleKey` (`modules.findByKey` returns `null` → `false`), and a misspelled _action_ string simply never matches any seeded `role_permissions.action` value, so `hasGrant` returns `false` — both failure modes fail closed (nobody can pass), not open (everybody can pass)                                                                                                                                                                                                           | The failure is "route is permanently inaccessible to everyone," an availability bug that integration tests would catch quickly (as they did for every real route in this phase), not a security hole — same fail-closed-by-construction property as the missing-decorator case above                                                                                                   |

## Summary of accepted gaps (not fixed in Phase 1D, tracked here rather than silently absent)

1. **No separation-of-duties check on role self-assignment** — a Super Admin can freely change their own roles with no second approver (see the Elevation of Privilege row above) — the most significant open item in this pass, explicitly flagged for the second-role reviewer's decision.
2. **No persisted audit trail for denied permission checks** — only successful role changes are recorded in `auth_events`; repeated denied attempts are visible only in ephemeral request logs.
3. **No "list permissions for a role" endpoint** — not a security gap (smaller surface is safer), but means the full grant matrix isn't independently auditable over HTTP yet; noted since a future module might need it.
4. **No dedicated concurrency test for the assign-role check-then-act race** — the database unique constraint is believed sufficient (see the last Elevation of Privilege row) but hasn't been exercised under real concurrent load.
5. **Confidential-field axis unimplemented** — `view_confidential`/`edit_confidential` are defined in the action vocabulary but never seeded or checked; carried over unchanged from the migration's own documented scope, not new to this pass.

None of these are believed to constitute a critical, immediately-exploitable vulnerability at this project's current stage (no production deployment, no real users) — they are scoped, documented risk-acceptance decisions (or, for #1, an open decision) consistent with `docs/task-packages/phase-1d-rbac-authorization.md`'s explicit scope, surfaced here for the required second-role review rather than left implicit.

## Resolution note (added by the Phase 1D expansion, not part of the original pass)

Accepted-gap #1 above ("no separation-of-duties check on role self-assignment") is **now closed**,
under `docs/task-packages/phase-1d-rbac-permissions-expanded.md` §21/§33's explicit instruction
("Do not allow self-assignment of privileged roles") — the user's own direction on this brief, not
a unilateral resolution of a gap this document deliberately left open for the second-role
reviewer. `RoleAssignmentService.assignRole`/`revokeRole` now call
`SeparationOfDutiesService.assertDistinctActors` before any other check, recording a
`separation_of_duties_denied` auth event on denial. This historical row is left unmodified above
(the gap was real at the time this document was authored); see
`docs/implementation/phase-1d-security-review.md` for the expanded pass covering this and the rest
of the Phase 1D-expanded surface. Accepted-gap #5 ("confidential-field axis unimplemented") is
likewise now partially addressed — see that document's own confidential-field section.
