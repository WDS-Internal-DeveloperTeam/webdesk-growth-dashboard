# Threat Model — Authentication and Session Handling (Phase 1C)

**Status:** Draft STRIDE pass, produced per `docs/security/threat-model-plan.md`'s procedure at the
point these two "Required coverage" areas moved from Architecture Defined to actual implementation
(Google Workspace SSO, ADR-0008; restricted emergency-administrator TOTP, ADR-0009; session
issuance/expiry/invalidation). Covers exactly the scope
`docs/task-packages/phase-1c-authentication-sessions.md` implements — RBAC (ADR-0010) and the
general audit-log subsystem (ADR-0017) are separate, not-yet-implemented areas with their own
future STRIDE passes.

**Review status:** authored by the same agent that implemented this phase. Per
`docs/security/threat-model-plan.md`'s procedure and ADR-0010's separation-of-duties principle,
this pass requires review by a second, human role before the implementation is considered ready
for its QA gate (G4) — that second review has **not** happened yet. This document is a rigorous
self-review, not a substitute for it; do not treat it as satisfying the gate on its own.

---

## Scope

- Google Workspace OIDC authorization-code+PKCE flow (`apps/dashboard-api/src/auth/google`).
- Restricted local emergency-administrator TOTP flow, two steps (`apps/dashboard-api/src/auth/emergency`).
- Session issuance, cookie handling, expiry, and revocation (`apps/dashboard-api/src/auth/session`).
- Account lockout / rate limiting (`apps/dashboard-api/src/auth/common/rate-limit.service.ts`).
- CSRF defenses (OAuth `state`/PKCE; `OriginCheckGuard`).

## Out of scope for this pass

RBAC/authorization enforcement (ADR-0010, Task 6 — not implemented yet, so nothing to threat-model
here beyond "authentication establishes identity only," already true today since no permission
model exists to bypass). The general ADR-0017 audit-log subsystem (Task 7). Vercel deployment/
infrastructure-level concerns (TLS termination, DDoS protection) — assumed provided by the hosting
platform, not this application layer.

## STRIDE — Authentication (Google SSO)

| Threat                                                                   | Scenario                                                                                                                                        | Mitigation                                                                                                                                                                                                                                                                                                                        | Residual risk                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spoofing** — forged ID token                                           | An attacker crafts a JWT claiming to be a WebDesk user                                                                                          | `openid-client`'s `authorizationCodeGrant` verifies issuer, audience, signature (against Google's published JWKS), and expiry before `claims()` returns anything — a token failing any check throws and the whole exchange fails closed (`google-auth.service.ts` `handleCallback`'s `catch` → `reject("token_exchange_failed")`) | None identified beyond trusting `openid-client`'s own correctness — an established, widely-used library, not reimplemented here                                                                                                                                                                                      |
| **Spoofing** — wrong-domain account                                      | A real Google account outside `webdesksolution.com`/`webdeskinc.com` attempts login                                                             | `hd` claim (falls back to email domain) checked against `GOOGLE_WORKSPACE_ALLOWED_DOMAINS`; rejected before any user lookup                                                                                                                                                                                                       | `hd` is Google-asserted, not independently verifiable beyond trusting the token's own signature (already covered above)                                                                                                                                                                                              |
| **Spoofing** — login for an unprovisioned/wrong user                     | A valid Google Workspace account with no matching pre-provisioned `users` row                                                                   | Pre-provisioned-only model (resolved this session): `UserRepository.findByEmail` must return a real, `active` row or the login is rejected — no JIT account creation                                                                                                                                                              | None — this is the primary defense the provisioning-model decision exists for                                                                                                                                                                                                                                        |
| **Tampering** — authorization-code interception/replay                   | An attacker who intercepts the authorization code (e.g., via browser history, referrer leak, malicious extension) tries to redeem it themselves | PKCE (`code_challenge`/`code_verifier`) binds the code to the specific browser session that started the flow; the code alone is insufficient without the verifier, which never leaves the OIDC transaction cookie                                                                                                                 | The transaction cookie itself is httpOnly (JS-inaccessible) but not further encrypted — see "OIDC transaction cookie" note below                                                                                                                                                                                     |
| **Tampering** — OIDC transaction cookie modified in transit/by client    | Client-side JS or a MITM alters the state/nonce/verifier before the callback                                                                    | httpOnly prevents JS tampering; a modified value simply fails `expectedState`/`expectedNonce`/`pkceCodeVerifier` checks inside `authorizationCodeGrant`, causing the exchange to fail closed, not to succeed with attacker-controlled values                                                                                      | Requires TLS (Secure cookie flag in production) to prevent network-level tampering — an accepted dependency on the hosting platform's TLS termination, not re-implemented at the application layer                                                                                                                   |
| **Repudiation** — no record of who logged in / was rejected              | An incident review can't tell who authenticated or why a login failed                                                                           | Every successful and rejected SSO login records an `auth_events` row (`sso_login_succeeded`/`sso_login_rejected`) with a generic, non-enumerating `reason`                                                                                                                                                                        | The full ADR-0017 audit subsystem (immutable at the DB-permission level, 7-year retention) is Task 7 — `auth_events` here is append-only _by construction_ (no update/delete method exists on `AuthEventRepository`) but not yet DB-permission-enforced                                                              |
| **Information Disclosure** — user enumeration via login error            | An attacker probes different emails to learn which ones have dashboard accounts                                                                 | Every rejection path (wrong domain, no matching user, disabled account) returns the identical generic `{ ok: false }` / HTTP 401 "Invalid credentials"-shaped response; the specific `reason` is recorded only in `auth_events`, never returned to the caller                                                                     | None identified for the SSO path itself                                                                                                                                                                                                                                                                              |
| **Denial of Service** — authorization-flood against `/auth/google/start` | Repeated hits generate load (PKCE computation, cookie writes)                                                                                   | No rate limiting is applied to `/auth/google/start`/`/callback` specifically — relies on the hosting platform's own DDoS/rate protections                                                                                                                                                                                         | **Accepted gap**: application-level rate limiting on the SSO endpoints themselves is not implemented in Phase 1C; the emergency-local path has its own lockout because it's the higher-value target (credential-guessing), the SSO path's abuse surface is more about resource exhaustion than credential compromise |
| **Elevation of Privilege** — n/a                                         | No privilege levels exist yet (RBAC is Task 6)                                                                                                  | —                                                                                                                                                                                                                                                                                                                                 | Authentication establishing only identity, not authorization, limits blast radius until RBAC exists                                                                                                                                                                                                                  |

## STRIDE — Authentication (Emergency-administrator TOTP)

| Threat                                                                      | Scenario                                                                                                                                        | Mitigation                                                                                                                                                                                                                                                                                                                                                                       | Residual risk                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spoofing** — password guessing                                            | Brute-force/dictionary attack against the password step                                                                                         | argon2id hashing (slow, memory-hard); `AuthLockoutStateRepository` + `RateLimitService` lock the `(scope="emergency_login", identifier=email)` pair after `AUTH_LOCKOUT_MAX_ATTEMPTS` failures for `AUTH_LOCKOUT_DURATION_SECONDS`; verified end-to-end in `test/auth.e2e-spec.ts`'s lockout test (a _correct_ password is rejected once locked)                                 | Lockout is per-identifier (email), so an attacker distributing guesses across many _unknown_ emails isn't slowed by this mechanism alone — mitigated by the dummy-hash timing-safety measure below, which makes each individual guess cost roughly the same regardless of account existence, but doesn't rate-limit by source IP. IP-based rate limiting is not implemented in Phase 1C (accepted gap, same rationale as the SSO endpoint)                                                    |
| **Spoofing** — TOTP guessing                                                | Brute-force against the 6-digit code once past the password step                                                                                | Separate lockout scope (`emergency_totp`, keyed by _session id_, not email) — a compromised password alone doesn't grant unlimited TOTP attempts; window is ±1 step (30s), not wide                                                                                                                                                                                              | 6-digit codes have a 1-in-1,000,000 space per window; combined with the lockout (3 attempts default) this is a strong practical defense, but is not a formal proof of security against a very fast, distributed guesser within a single window — accepted, standard TOTP risk                                                                                                                                                                                                                 |
| **Spoofing** — user enumeration via timing                                  | Measuring response time to infer whether an email has an emergency-admin credential                                                             | `getDummyHash()` runs a real argon2 verify against a fixed dummy hash for unknown/inactive accounts, so the password-verification step takes comparable wall-clock time whether or not the account exists (`emergency-admin.service.ts`)                                                                                                                                         | This is a mitigation, not a formal constant-time guarantee — database lookup time, network jitter, and JIT warm-up could still leak a weaker timing signal. Not considered a practical risk at this project's threat level (internal tool, small user base)                                                                                                                                                                                                                                   |
| **Tampering** — TOTP secret at rest                                         | Database compromise exposes TOTP secrets                                                                                                        | AES-256-GCM encryption (`totp-encryption.ts`) — GCM's authentication tag means a tampered/corrupted ciphertext fails to decrypt rather than silently succeeding with wrong data; verified in `totp-encryption.spec.ts`'s tamper test                                                                                                                                             | The encryption key (`TOTP_ENCRYPTION_KEY`) itself must be protected per `docs/security/secrets-management-plan.md` — a database compromise _combined with_ the encryption key's compromise defeats this control, an inherent limit of application-layer encryption with a single key                                                                                                                                                                                                          |
| **Tampering** — password hash at rest                                       | Database compromise exposes password hashes                                                                                                     | argon2id — computationally expensive to crack even offline; industry-standard choice, matches base-skill recommendation                                                                                                                                                                                                                                                          | Standard password-hash risk profile; no additional pepper/HSM-backed key is used, consistent with this project's V1 scope (`docs/security/secrets-management-plan.md` explicitly scopes out a dedicated secrets service)                                                                                                                                                                                                                                                                      |
| **Repudiation** — emergency access goes unnoticed                           | An emergency-admin login happens and nobody reviews it                                                                                          | Every attempt (success/failure at either step, including lockout) records a distinct `auth_events` row (`emergency_login_succeeded`/`emergency_login_failed`/`emergency_totp_failed`/`account_lockout_triggered`); a successful login also calls `EmergencyAdminLoginNotifier.notify()`                                                                                          | The notifier's only implementation (`LoggingEmergencyAdminLoginNotifier`) writes a log line — the real SMTP alert to the Security/DevOps distribution list (knowledge/05) is **not wired**, since Google Workspace SMTP integration doesn't exist yet (out of Phase 1C's scope, per the task package). **This is the most significant accepted gap in this pass**: until SMTP is wired, emergency-admin access relies on someone actively reading logs/`auth_events`, not a push notification |
| **Information Disclosure** — no self-service account creation               | Someone tries to create their own emergency-admin credential via an API                                                                         | No HTTP endpoint exists for credential creation — only the operator-run CLI script (`provision-emergency-admin.ts`), which requires direct database/server access, not reachable over the network                                                                                                                                                                                | None identified                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Denial of Service** — lockout as a griefing vector                        | An attacker deliberately fails login attempts against a known emergency-admin email to lock out the legitimate admin during an actual emergency | This is the classic account-lockout-enables-DoS tradeoff — accepted per knowledge/05's own design (lockout is required baseline). Mitigated by: (a) the recovery-request foundation (`RecoveryService`) allowing a second administrator to help recover access, and (b) the lockout duration being bounded (`AUTH_LOCKOUT_DURATION_SECONDS`, default 15 minutes), not indefinite | If the _only_ emergency admin is locked out during a genuine SSO outage with no second admin available to approve recovery, there is no automated unlock — an accepted, documented operational risk inherent to any lockout policy, not unique to this implementation                                                                                                                                                                                                                         |
| **Elevation of Privilege** — pending session used as if fully authenticated | An attacker who steals a pending (password-verified, MFA-not-yet-verified) session token tries to use it as a full session                      | `SessionService.validate()` explicitly rejects any session with `requiresMfa: true` — a pending session is never accepted by `GET /auth/session` or any future RBAC-gated endpoint                                                                                                                                                                                               | The pending session cookie itself is a bearer credential for the _TOTP step specifically_ — if stolen within its short window (`SESSION_PENDING_MFA_MAX_AGE_SECONDS`, default 5 minutes), an attacker who also somehow has the TOTP code could complete the login. This requires compromising two independent factors within a short window — consistent with defense-in-depth expectations for 2FA                                                                                           |

## STRIDE — Session handling

| Threat                                                                                | Scenario                                                                                                                      | Mitigation                                                                                                                                                                                                                                                                                                              | Residual risk                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Spoofing** — session fixation                                                       | An attacker sets a known session token on a victim's browser before login, hoping to hijack it after the victim authenticates | Every login (SSO or emergency) mints a brand-new, freshly-generated token via `generateSessionToken()` (32 bytes of `crypto.randomBytes`) — no code path accepts a client-supplied token as the session identifier                                                                                                      | None identified                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Spoofing/Tampering** — session hijacking via database read                          | An attacker who can read the database tries to use a `token_hash` value directly as a session credential                      | `token_hash` is a one-way SHA-256 digest — the raw token (the actual bearer credential) is never persisted, only ever held by the issuing response and the client's cookie jar; a stolen hash cannot be replayed as a token                                                                                             | None identified — this is exactly the property the hash-not-raw-token design exists for                                                                                                                                                                                                                                                                                                                                         |
| **Tampering** — cookie forgery                                                        | An attacker crafts an arbitrary cookie value hoping to be treated as a valid session                                          | `SessionService.validate()`/`findPending()` look up by the SHA-256 hash of whatever was supplied — a forged value simply won't match any `token_hash` row, `findByTokenHash` returns `null`, and the request is rejected                                                                                                | None identified — no signature or predictable structure exists in the token for an attacker to exploit; it's pure high-entropy randomness                                                                                                                                                                                                                                                                                       |
| **Repudiation** — logout/revocation not recorded                                      | A session is revoked but there's no record of when or why                                                                     | `SessionService.revoke()`/`revokeAllForUser()` both call `AuthEventRepository.record()` with `eventType: "session_revoked"` and the reason (`user-initiated`/`role-change`/`admin-forced`/`security-incident`/`expired`) before returning                                                                               | `"expired"` as a reason is defined in the type but no code path currently calls `revoke()` with it — natural expiry is currently detected only at validation time (`expiresAt <= now`) and never explicitly recorded as a revocation event, since nothing writes to the row when it merely lapses. This is a minor, accepted gap: an expired session is invisible in `auth_events` until/unless something explicitly revokes it |
| **Information Disclosure** — session cookie leakage via logs                          | The session cookie value ends up in application logs                                                                          | `app.module.ts`'s pino redaction list explicitly includes `req.headers.cookie` and `res.headers["set-cookie"]`, plus `req.body.password`/`req.body.code` for the emergency endpoints                                                                                                                                    | Redaction is a `pino` configuration, not a structural guarantee — a future log statement that manually interpolates a cookie/password into a message string would bypass it. No such call exists today (verified by inspection), but this is a class of risk redaction can't fully close by itself                                                                                                                              |
| **Information Disclosure** — session cookie leakage via XSS                           | A successful XSS attack reads the session cookie via `document.cookie`                                                        | `httpOnly: true` on every session/OIDC-transaction cookie set (`cookie.util.ts`, `oidc-transaction.ts`) — JavaScript cannot read these cookies at all, regardless of an XSS vulnerability elsewhere in the app                                                                                                          | Does not protect against an XSS attacker directly _using_ the browser's authenticated session (e.g., issuing fetches with `credentials: "include"`) — httpOnly stops cookie _exfiltration_, not in-session action-riding by a script running in the authenticated page. No XSS vulnerability is known to exist in this codebase; this is a general property of cookie-based auth, not specific to this implementation           |
| **Denial of Service** — session-table growth                                          | Unbounded session creation exhausts storage                                                                                   | No explicit cap on sessions per user or global cleanup job for expired/revoked rows exists in Phase 1C                                                                                                                                                                                                                  | **Accepted gap**: a retention/cleanup job for old session rows (similar in spirit to ADR-0017's audit-retention job) is not built — Phase 1C's own scope is issuance/validation/revocation, not lifecycle housekeeping. Should be revisited alongside Task 7's audit-retention background job, since both are "old append-heavy table needs periodic archival/cleanup" problems                                                 |
| **Elevation of Privilege** — cross-site request using an authenticated session (CSRF) | A malicious site tricks a logged-in admin's browser into POSTing to `/auth/logout` or the emergency endpoints                 | `SameSite=Strict` on the session cookie (not sent on cross-site requests at all, for these state-changing endpoints) plus `OriginCheckGuard` as an independent second check comparing Origin/Referer against the configured `WEB_APP_ORIGIN` — verified in `origin-check.guard.spec.ts` and the e2e suite's guard tests | The OIDC transaction cookie is deliberately `SameSite=Lax` (required so it survives Google's own top-level redirect back to the callback) — this is a narrower, well-understood exception, not a general CSRF weakening, since that cookie alone grants no access (see the Authentication/Google-SSO table's Tampering row)                                                                                                     |

## Summary of accepted gaps (not fixed in Phase 1C, tracked here rather than silently absent)

1. **No SMTP delivery for emergency-admin login alerts** — logged only, not emailed (blocked on Google Workspace SMTP integration, a separate task).
2. **No IP-based rate limiting** on SSO or emergency-login endpoints, only per-identifier lockout for the emergency path.
3. **No explicit `"expired"` revocation event** — natural expiry is silent in `auth_events` until something else revokes the row.
4. **No session-table retention/cleanup job.**
5. **No automated unlock path if the sole emergency admin is locked out with no second admin available** — inherent to any lockout policy; the recovery-request foundation mitigates but doesn't eliminate this.

None of these are believed to constitute a critical, immediately-exploitable vulnerability at this project's current stage (no production deployment, no real users, no real Google OAuth client yet) — they are scoped, documented risk-acceptance decisions consistent with `docs/task-packages/phase-1c-authentication-sessions.md`'s explicit out-of-scope list, surfaced here for the required second-role review rather than left implicit.
