# 00 — Scope and Precedence

> Read this before any other file in this profile. It governs how every other file here is meant to be read when it appears to say something different from the base skill, the dashboard documentation, or a project ADR.

---

## 1. The precedence order

1. **Approved WebDesk Dashboard Master Specification** — `webdesk-dashboard-documentation-v1/01_Dashboard_Master_Specification.md`.
2. **Approved detailed dashboard documentation** — the remaining 11 documents in `webdesk-dashboard-documentation-v1/`, plus any registered canonical project document (WordPress Technical Discovery, Agent Specification Batch N, Service/SEO Library exports — see §4).
3. **Approved WebDesk project decisions and ADRs** — architecture decision records produced under the project's `docs/architecture/adr/` once Phase 0 begins, using `templates/architecture-adr-template.md`.
4. **This project profile** — everything under `profiles/webdesk-growth-dashboard/`.
5. **WebDesk Node.js base skill** — `nodejs/SKILL.md` and everything under `nodejs/knowledge/`, `nodejs/projects/custom-app-build/`.
6. **General Claude Code conventions.**

This list is a **strict total order**, not a weighting. A lower-numbered source always wins over a higher-numbered one on the specific point where they conflict — there is no averaging or "mostly follow the skill but adjust for the spec."

---

## 2. What counts as a conflict

A conflict is when two sources at different precedence levels give **incompatible instructions on the same concrete point** — not merely when one is silent and another isn't (silence is not conflict; the more specific source simply fills the gap, per normal precedence). Examples:

- **Conflict:** the base skill's `technology-selection.md` names Express as the default backend framework; the Master Specification names NestJS. → Not actually a conflict once resolved: the Master Specification is precedence level 1, and the base skill's own "ask-if-missing, record the override" rule is exactly the mechanism for this — see `knowledge/03-nestjs-on-vercel.md`. This is the _pattern_ of how "conflicts" here usually resolve cleanly: a higher-precedence source states an approved override of a lower-precedence default, and the profile records it. This is not escalation-worthy.
- **Genuine conflict requiring escalation:** if a future dashboard-documentation update stated a requirement that directly contradicted an already-approved ADR (e.g., the Master Specification is revised to require a different job-execution model than the one resolved in `knowledge/04-serverless-queues-workflows-and-cron.md`), that is a real conflict between precedence level 1 and level 3 content, and must not be silently resolved by picking whichever a given agent read most recently.

**The test:** if resolving the disagreement requires guessing what a human intended, it's a conflict to escalate. If resolving it just requires applying the precedence order to two sources that both remain internally consistent (a default vs. an approved override of that default), it's not — record the resolution and move on.

---

## 3. What to do on a genuine conflict

1. **Do not silently choose.** Do not proceed with either interpretation without flagging it.
2. **Follow the higher-precedence approved source** for the purposes of continuing the current task, if the task cannot simply pause.
3. **Record the conflict** — in the active task's package/handoff notes at minimum; in `docs/skill-build/unresolved-items.md` if it appears to be a standing conflict rather than a one-off ambiguity in a single task's instructions.
4. **Escalate when the higher-precedence source does not clearly resolve it** — surface to the PM role / project lead rather than guessing. This mirrors `nodejs/knowledge/technology-selection.md`'s "ask-if-missing" rule, applied to conflicts between approved sources instead of to missing tech-stack layers.

Never resolve a conflict by editing the base skill to "fix" it (see `SKILL.md` §5, Base-skill protection) and never resolve it by silently editing the dashboard documentation pack — both are read-only inputs to this profile, not outputs of it.

## 5. Two agent taxonomies

Restated from `SKILL.md` §6 because it is easy to get wrong mid-task, especially once Agent Specification Batch content is registered:

- **Software-delivery roles** (PM, Architect, Backend, Frontend, Designer, QA, Code Review, Delivery Head) build and review the dashboard application. They are defined by `_spine/*/SKILL.md` in the base skill. This profile configures _how_ they work on this project; it does not add new roles to this taxonomy and does not rename any of them.
- **Dashboard business/delivery agents** (Website Growth Director, Site Intelligence and Inventory Agent, Search Strategy Agent, Content Strategy Agent, Case Study and Portfolio Agent, Creative Director, UX/CRO Agent, UI Design System Agent, WordPress Engineering Agent, Dashboard Application Engineering Agent, Code Review Agent, Security Assurance Agent, QA/Accessibility/Performance Agent, Release and Memory Coordinator, Product Documentation Agent) are **product data** the finished dashboard stores and governs through its own Agent Directory (module #26) and Agent Specification Library (module #27), in the approved nineteen-section format. Building the dashboard code that stores and displays these records is software-delivery-role work (taxonomy 1); the specification _content itself_ is taxonomy 2 data.

Note the naming collision: two entries above are literally named "Code Review Agent" — one is this delivery system's own PR-review role (taxonomy 1), the other is a dashboard business agent that reviews _website/content_ work as part of the page-workflow gates (taxonomy 2). They are unrelated despite the shared name. When a task mentions "Code Review Agent" without further context, confirm which taxonomy is meant before proceeding — do not assume.

`docs/implementation/open-questions.md` OQ-04 asked whether the Agent Directory/Specification Library modules mirror the software-delivery roster or define a distinct taxonomy. **This is resolved, not ambiguous:** they are a distinct, separate taxonomy — the two are never merged, per the skill-build task's own §12. Batch 1, now registered as canonical project documentation (§4 above), independently confirms this resolution rather than leaving it open: its `00_README.md` names the 19-section format explicitly (agent name, mission, business purpose, responsibilities, decisions owned, decisions not owned, required inputs, knowledge library, tools and permissions, workflow, output files, quality checklist, approval gates, forbidden actions, escalation rules, memory read/write responsibilities, dashboard interface, test scenarios, version/review schedule) and a precedence order (repo implementation → production website → approved state records → approved registries → approved strategy → roadmap → draft/advisory records → conversation context) that matches this profile's own precedence model closely, with no attempt to fold the four Batch 1 agents into the software-delivery roster. **The only thing genuinely still open** is a narrower, non-blocking implementation detail: Batches 2–4 (the remaining eleven business agents) have not yet been supplied, so the full fifteen-agent set cannot be cross-checked against this format yet — that is a future-supply item, not an ambiguity about which taxonomy governs.

## 6. Spreadsheet and export data

Where a Service and SEO Library export (or any similarly-sourced spreadsheet/CSV data) is registered under §4, treat its content as **advisory sample data pending review** — usable to understand shape and scale (how many services, how many keywords, what fields recur), never as pre-approved business content to ship into the Service Library or Keyword and Entity Library without going through the dashboard's own approval workflow (`03_Detailed_Module_Specifications.md §20/§23`: "SEO-team data is advisory until Search Strategy and Growth Director review, followed by human approval"). This applies even to Batch 1 agent specifications and any other document registered under §4 that has not itself been through an explicit approval gate.
