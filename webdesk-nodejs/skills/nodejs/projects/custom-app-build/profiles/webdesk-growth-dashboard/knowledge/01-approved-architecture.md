# 01 — Approved Architecture

> Every item below is **approved and kept**, per `docs/implementation/architecture-validation.md`. This file states the resolved stack as an operating fact for implementation; it does not re-litigate the choice. Where a component is genuinely new territory for the base skill, the adaptation knowledge lives in the numbered file referenced in the right column — read that file before implementing the corresponding piece.

## Application structure

Turborepo monorepo, one repository (`webdesk-growth-dashboard`):

```text
apps/
├── dashboard-web/       Next.js App Router frontend
├── dashboard-api/       NestJS backend, deployed as Vercel Functions
└── dashboard-worker/    NOT a persistent process — Vercel Function handlers
                          behind Vercel Queues / Workflows / Cron Jobs

packages/
├── database/            Sequelize models, migrations — single migration owner
├── shared-types/        Cross-app TypeScript types
├── validation/          Zod schemas — single source consumed by web, api, and
                          NestJS validation pipes
├── ui/                  Shared React components, design tokens
├── integrations/        GitHub, WordPress, Google Workspace, Vercel adapters
└── configuration/       Env schema, shared config loading
```

Boundary and build-graph detail: `knowledge/02-turborepo-boundaries.md`.

## Database — the one item requiring a stop condition

PostgreSQL is the engine choice (matches the base skill's own default, no justification needed for the engine itself). The provisioning constraint is:

- **Provisioned and connected through Vercel, in an approved North America East Coast environment.**
- **Neon is excluded as a directly selected project provider.**
- **Do not introduce provider-specific PostgreSQL business logic** — application code talks to standard PostgreSQL via Sequelize; no code path assumes a specific managed-Postgres vendor's proprietary extensions or connection-pooling API beyond standard `pg`/Sequelize configuration.
- **The exact Vercel Marketplace provider is an environment setup value**, recorded in `project.json` / environment configuration once actually provisioned — not decided in this skill build (see `templates/project.json.example` and `docs/skill-build/unresolved-items.md`).

**Stop condition:** if, at provisioning time, Vercel cannot offer a qualifying North America East Coast PostgreSQL option without violating the Neon exclusion (e.g., every Vercel-integrated Postgres marketplace option is Neon-based) — **stop**. Document the conflict in `docs/skill-build/unresolved-items.md` (or its Phase-0-era successor), request an infrastructure decision from the project's technical/infrastructure owner, and do not silently substitute a different provider or a different region to route around the conflict. This is the direct resolution mechanism for `docs/implementation/open-questions.md` OQ-01, which this profile does not resolve on its own authority because it is an infrastructure-availability fact, not an architecture preference.

## Region policy (applies uniformly)

All dashboard production infrastructure — Vercel applications, PostgreSQL, Upstash Redis, Vercel Blob, WordPress.com, and backup storage — is North America East Coast. No production application data is intentionally stored in India or Singapore, for any component, including third-party subprocessors selected during implementation. This is a hard constraint, not a default to weigh against cost or convenience.
