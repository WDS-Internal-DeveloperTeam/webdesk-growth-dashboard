# 13 — Testing and Acceptance

> The base skill's testing stack (`nodejs/knowledge/testing/01-03`) and the dashboard's own acceptance criteria (`11_Acceptance_Criteria_and_Test_Plan.md`) cover nearly identical ground independently. This file is the mapping between them plus the project-specific tooling substitution (Vitest/Jest over `node:test`) and the serverless-execution adaptation for load/chaos testing.

---

## Load and chaos testing under the serverless model

`nodejs/knowledge/testing/02-load-and-chaos.md`'s k6/Artillery guidance assumed a persistent process under test. Under `knowledge/04-serverless-queues-workflows-and-cron.md`'s resolved model:

- **Baseline/peak/stress load** targets `dashboard-api`'s Function endpoints directly — same k6/Artillery tooling, same SLO assertions (p95/p99 latency, error rate), different target shape (Functions cold-start behavior and platform-managed concurrency limits replace a single server's connection-pool ceiling as the thing under test).
- **Queue/workflow throughput** is measured indirectly — enqueue at volume via the `JobQueueAdapter`, measure end-to-end job completion latency and watermark lag, since there is no worker process to attach a load generator to directly.
- **Chaos/fault-injection matrix** (`testing/02`'s table) still applies row-for-row; "kill the sync mid-run" becomes "a Function invocation times out or is recycled mid-handler," which the required job-record properties (`knowledge/04`) already handle identically in outcome (resume from the last-committed watermark) even though the failure's _mechanism_ differs from a killed persistent worker.
